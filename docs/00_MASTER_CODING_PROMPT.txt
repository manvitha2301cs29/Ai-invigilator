I'm building a project called "AI Study Invigilator." Act as a senior
full-stack + ML engineer helping me build it incrementally, phase by
phase. Read this entire brief before writing any code.

PROJECT SUMMARY
A system that helps a motivated-but-inconsistent student hold themselves
to self-set study blocks. The student sets a target block (e.g. 12:00 to
13:30). While the block is active, a local Python process watches the
webcam continuously (independent of any browser tab, so it keeps working
while the student uses other tabs like LeetCode) and classifies behavior
into: Engaged, Idle-present, Distracted-present, or Away. The moment the
student leaves the desk, a stopwatch starts automatically and stops when
they return. If a phone is detected in frame for a sustained period, fire
a direct notification: "Don't use your phone, {name}." If a second person
is detected in frame for a sustained period, fire a direct notification:
"Stay in a quiet environment -- avoid talking to others, {name}." At the
end of the block, the student sees exactly how much time was worked, how
much was on a declared break, and how much was lost to being away or
distracted, plus a personalized recommendation (shrink the block, extend
it, or add a scheduled break) based on their OWN historical compliance
trend -- not a generic rule.

NON-NEGOTIABLE DESIGN PRINCIPLES (do not deviate from these)
1. PRIVACY: never persist raw video frames to disk or database. Only
   numeric features and derived statistics are stored. Frames are
   processed in memory and discarded immediately after feature
   extraction.
2. NO MENTAL-STATE CLAIMS: the system classifies observable behavior
   only (face orientation, gaze, posture, presence, movement, phone
   presence). It never claims to detect emotions or "focus" as a mental
   state. Prolonged eye closure is labeled "possible rest/sleep," an
   inference, never asserted as fact.
3. DURATION-GATED FLAGS: no state or warning is ever decided from a
   single frame. Every flag (away, distracted, phone-use, prolonged
   eye-closure) requires a signal to persist past a duration threshold.
   Specifically:
   - Note-taking (sustained head-down WITH a periodic look-up cycle)
     must NOT be flagged as distracted.
   - A brief head turn (a glance, checking a second monitor) must NOT be
     flagged; only a SUSTAINED head turn (implying conversation) should
     flag as Distracted-present.
   - Gaze tolerance must be calibrated per-user (a short "look at your
     screen corners" calibration step at first run) so wide or
     multi-monitor setups don't misread as constant distraction.
   - Brief eyes-closed (a few seconds, thinking) must NOT be flagged.
     Only eyes-closed sustained past ~6 minutes (configurable) should
     flag, worded as "possible rest/sleep."
   - A phone glimpsed briefly must NOT be flagged. Only a phone visible/
     held for a sustained duration should trigger the named warning
     "Don't use your phone, {name}."
   - A second person glimpsed briefly (someone walking past in the
     background) must NOT be flagged. Only a second face present
     continuously for a sustained duration should trigger the named
     warning "Stay in a quiet environment -- avoid talking to others,
     {name}." This reuses the same Face Landmarker already running for
     the primary student (configure it for up to 2 faces) rather than a
     separate model -- no new dependency needed.
4. DETERMINISTIC LOGIC IS SEPARATE FROM LLM OUTPUT: all numbers
   (compliance %, worked time, away time, verdict category) are computed
   by plain, testable, deterministic code. The LLM (Claude API) is used
   ONLY to phrase the final natural-language message from those
   already-computed numbers -- it must never be the source of a number
   or a verdict category itself.
5. TWO-PART DEPLOYMENT ARCHITECTURE: this is NOT a single website.
   - A LOCAL WATCHER: a Python process that runs on the student's own
     machine, owns the webcam continuously, and keeps working even when
     the student's browser is on a different tab or the browser is
     minimized. It sends only extracted features/state events (never
     video) to a backend API over HTTP/WebSocket.
   - A SHARED WEB DASHBOARD: a normal deployed website (public URL,
     anyone with the link can view their own account's data) for
     planning target blocks, viewing live status as reported by the
     watcher, session history, and recommendations. It does NOT access
     the webcam itself.
   Explain this split back to me in your own words before starting, so
   I know you understood it, then proceed.

TECH STACK
  - Perception: Python, OpenCV, MediaPipe (Face Landmarker, Pose
    Landmarker, Object Detector using the EfficientDet-Lite0 model for
    phone detection -- it's COCO-pretrained and already includes a
    "cell phone" class, so no custom training data is needed for this
    part)
  - Deep learning: PyTorch (GRU primary temporal model; LSTM and a small
    Transformer encoder as comparison baselines; a separate autoencoder
    for fatigue-pattern anomaly detection)
  - Backend: FastAPI, PostgreSQL from the start (not SQLite) -- this
    project targets real production deployment so others can use it,
    and SQLite's single-writer model doesn't hold up behind a public
    multi-user backend. Run Postgres locally via Docker during
    development (docker-compose) so local dev is architecturally
    identical to what gets deployed later. Use SQLAlchemy 2.x
    (DeclarativeBase + Mapped[]/mapped_column style) with the psycopg
    (v3) driver.
  - Frontend: React (Vite) -- component-based, clean, functional
    components with hooks, Tailwind for styling
  - LLM: Claude API (Anthropic), called only from the backend, never
    the frontend or the watcher
  - Local watcher <-> backend communication: simple authenticated HTTP
    POST for state events; a WebSocket connection for live status so the
    dashboard can show real-time state without polling

DATA MODEL (implement exactly this, adjust types to your ORM/framework)
  TargetBlock: id, user_id, planned_start, planned_end,
    planned_duration_min, status [scheduled|active|completed|abandoned],
    actual_start, actual_end, created_at
  StateEvent: id, target_block_id, timestamp, state
    [engaged|idle_present|distracted_present|away], raw_features (JSON:
    yaw, pitch, roll, gaze_x, gaze_y, eyes_closed, posture_angle,
    movement_delta, face_conf, phone_detected, second_person_detected)
  BreakEvent: id, target_block_id, break_start, break_end, declared=true
  AwayEvent: id, target_block_id, away_start, away_end, duration_sec,
    was_notified
  PhoneEvent: id, target_block_id, detected_start, detected_end,
    duration_sec, was_notified
  SecondPersonEvent: id, target_block_id, detected_start, detected_end,
    duration_sec, was_notified
  TargetBlockSummary: target_block_id, worked_sec, distracted_sec,
    away_undeclared_sec, declared_break_sec, phone_flag_count,
    second_person_flag_count, away_event_count, compliance_pct, verdict
    [on_track|needs_shorter_blocks|needs_scheduled_breaks]
  User: id, name, email, auth fields as appropriate for your chosen auth
    approach

BUILD ORDER (we will do these as separate follow-up prompts in this same
conversation -- for now, just confirm you understand the full scope, ask

  Phase E: Autoencoder for fatigue-pattern anomaly detection.

TIPS FOR VIBE-CODING THIS EFFECTIVELY
================================================================================
- Keep this conversation thread going for the whole project rather than
  starting new chats per phase -- the assistant needs the accumulated
  context of earlier phases (file structure, naming, data model) to stay
  consistent.
- After each phase, actually run the code before moving on. It's much
  cheaper to say "Phase C's away-stopwatch doesn't reset correctly when
  I return before the grace period ends" than to discover it three
  phases later buried under more code.
- If the assistant's output drifts from the false-positive rules or the
  privacy/no-raw-video rules, quote the exact rule back at it from this
  file rather than re-explaining from scratch -- it re-anchors faster.
- Ask for unit tests at every phase where behavior is rule-based
  (Phase B, C's state machine, F). Deep learning phases (D, E) should
  instead get you an evaluation script with metrics, not unit tests.
