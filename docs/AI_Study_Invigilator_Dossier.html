EXHIBIT 01

The problem

Most students who struggle with study consistency aren't unmotivated — they're undermonitored. They sit down intending to focus for a fixed block, and drift, without ever finding out how much time was actually lost, or to what.

Generic advice — "take a break every 25 minutes" — isn't personalized, and it isn't earned. A student has no objective record of their own attention pattern to act on, so every piece of advice feels arbitrary, and arbitrary advice is easy to ignore.

This project is built for a specific person: motivated, but inconsistent. Someone who wants an honest, slightly strict observer — not a mental-health app, not a gamified streak-counter, something closer to an exam invigilator who happens to also be their tutor.

Explicit guardrail The system never claims to detect emotion or mental state. It classifies only observable signals — face orientation, gaze direction, posture, presence, movement, and coarse activity — and reports them as estimates with uncertainty, never as facts about what a student is thinking or feeling.
EXHIBIT 02

The core idea

A student sets a target study block. The system holds them to it — in real time — and reports back in numbers, not vibes.

1. Plan. The student sets a block: e.g. 12:00 to 13:30, "no-break study session." This is the target the whole session gets measured against.

2. Watch. While the block is active, the webcam and (optionally) OS activity signals are continuously classified into a behavioral state — Engaged, Idle-present, Distracted-present, or Away.

3. Time every absence. The moment the student leaves the desk, a stopwatch starts automatically. It stops the instant they return. This is tracked separately from a break the student explicitly declares.

4. Intervene, gently, live. If an absence runs long, the system nudges — softly at first, more directly if it continues — the way a strict-but-fair invigilator would, not a nagging app.

5. Report, honestly. At the end of the block: how much time was actually worked, how much was on a declared break, and how much was simply lost.

6. Learn the student, not a rulebook. Across weeks of blocks, the system compares the student's compliance trend against their own history — not a generic Pomodoro rule — and recommends whether to hold the schedule, shrink it, or extend it.

EXHIBIT 03

System pipeline

Eight layers, each independently testable. Raw pixels enter at the top; a phrased, personalized recommendation exits at the bottom. Nothing but numbers and short-lived frames cross between them.

01
Perception
Webcam frame → face detection, 468-point facial landmarks, body pose landmarks, presence detection, phone detection, second-person detection.
MediaPipe Face Landmarker (2-face) + Pose Landmarker + Object Detector — all pretrained, not retrained
02
Feature engine
Landmarks → clean numeric vector: head yaw/pitch/roll, gaze direction, eyes-closed flag, posture angle, movement delta, face-present flag, optional activity signal — plus two derived features, a look-up cycle rate (separates note-taking from disengagement) and a per-student calibrated gaze envelope (separates wide-monitor movement from genuine distraction).
Deterministic geometry — solvePnP, custom feature functions
03
Temporal deep learning model
A sliding window of feature vectors → engagement state. GRU is the deployed model; LSTM and a Temporal Transformer are trained as comparison baselines. Trained on the cycle-rate and gaze-envelope features specifically so it learns real behavioral patterns instead of a naive "any non-forward gaze = distracted" shortcut. Sustained eyes-closed beyond ~6 minutes is a separate deterministic rule, not a learned class.
PyTorch — GRU (primary), LSTM, Transformer encoder (ablation)
04
Live monitoring & stopwatch engine
Consumes the live state stream. Runs the away-detection state machine, fires escalating notifications, accepts user-declared breaks.
Real-time state machine, OS/browser notification API
05
Session analytics
Smooths state jitter, detects unbroken work stretches, computes per-block summaries: worked time, distracted time, away time, break time, compliance %.
Pandas / NumPy over logged StateEvents
06
Recommendation engine
Deterministic, auditable rules over the student's own historical compliance trend — decides on_track / needs_shorter_blocks / needs_scheduled_breaks. No model here — just transparent thresholds.
Rules engine, fully unit-testable in isolation
07
LLM reasoning layer
Takes only the structured verdict and numbers from Layer 6 — never raw video or per-frame data — and phrases a grounded, tone-appropriate recommendation.
Claude API — phrasing only, never the source of a number
08
Dashboard & storage
Statistics and features only — never raw video — served to a web dashboard.
FastAPI, SQLite/PostgreSQL, React/Next.js or Streamlit

Each layer can be built and tested with mocked input from the layer before it — the project is demoable at every milestone, not only at the end.

EXHIBIT 04

Behavioral state model

Four observable states, deliberately not a single "focused / not focused" binary — because "at the desk, not typing" and "not at the desk at all" are different problems that need different responses.

ENGAGED

Face present, gaze on-screen, recent input activity. The state that counts fully toward compliance.

IDLE-PRESENT

Face present, low movement, no recent typing. Reading or thinking — not penalized as distraction.

DISTRACTED-PRESENT

Face present, gaze repeatedly off-screen, or active window doesn't match the study context.

AWAY

Face absent beyond a short grace period. Triggers the automatic stopwatch — handled as a deterministic rule, not a learned class.

A fifth, session-level label — fatigued-pattern — is produced separately by an anomaly-detection model comparing a student's recent behavior to their own baseline, not to a population norm. It is never claimed as a diagnosis of tiredness, only as a statistical deviation worth surfacing.

EXHIBIT 05

False-positive handling

A naive "gaze not on screen = distracted" rule would misfire on almost every real study session. Note-taking, thinking pauses, wide monitors, and brief conversations all have to be told apart from genuine disengagement — and the difference is never in a single frame, only in the pattern over time.

Governing principle No state is decided from a single frame. Every flag requires a signal to persist past a duration threshold calibrated to what real studying looks like — not an idealized "always facing forward" assumption.
BehaviorFlag?Why
Brief head-down glanceNoUnder the note-taking window — too short to mean anything on its own.
Head down, writing notesNoRecognized by its look-down / look-up cycle — sustained down-pitch with periodic returns to the screen, not flat disengagement.
Head turned — quick glanceNoReturns to on-screen within a second or two — a wide monitor, a phone glance, checking a noise.
Head turned — talking to someoneYesHeld turned for a sustained duration — the hold, not the turn itself, is what's flagged.
Wide/multi-monitor eye sweepNoFalls inside a per-student calibrated gaze envelope, set once at first use — not a fixed universal angle.
Eyes closed briefly, thinkingNoNormal cognitive behavior during problem-solving — flagging it would be an unsupported claim about mental state.
Eyes closed 6+ minutesYesFar outside any thinking-pause range. Worded as "possible rest/sleep" — an inference, never asserted as fact.
Phone briefly passes through frameNoUnder the phone-visible duration floor — picked up and set back down, not sustained use.
Phone held / visible, sustainedYesA direct, personalized warning — "Don't use your phone, {name}" — since a phone in frame has fewer innocent explanations than an ambiguous gaze signal.
Second person briefly passes byNoUnder the second-person duration floor — someone walking past in the background, not sitting down.
Second person present, sustainedYesA direct, personalized warning — "Stay in a quiet environment, avoid talking to others, {name}". Known limitation: can't distinguish a study partner from a genuine distraction — flagged as an honest simplification, not solved.

The look-down/look-up cycle rate and a per-user calibrated gaze envelope are computed in the Feature Engine (Exhibit 03, Layer 2) specifically so the temporal model learns these distinctions instead of a naive "any non-forward gaze is distraction" shortcut.

EXHIBIT 07

Deep learning components

Built to be honest about what's a genuine contribution versus reused infrastructure — a distinction worth stating explicitly in any report or interview.

ComponentStatusWhy
Face & pose landmarksReused (pretrained)MediaPipe's landmark models are infrastructure — retraining them adds no value and no reasonable student dataset beats them.
Gaze / head-pose regressorBuilt from scratchLightweight geometric solvePnP baseline plus an optional small MLP over landmarks — competitive with heavier CNN baselines at a fraction of the cost.
Temporal engagement classifierBuilt from scratchGRU trained on windows of feature sequences; the project's central deep learning contribution.
LSTM / Transformer comparisonsBuilt from scratchTrained as ablation baselines against the deployed GRU — accuracy vs. latency vs. size tradeoffs, reported honestly.
Fatigue-pattern autoencoderBuilt from scratchReconstruction-error anomaly model comparing a student to their own baseline, not a population.
Recommendation engineBuilt from scratchDeterministic trend/threshold rules — not "ML" in the modeling sense, but a designed, testable algorithm.
Natural-language phrasingReused (API)Claude API — fine-tuning a language model is out of scope and adds nothing; the contribution is in prompt/context design.

Why GRU as the deployed model: sessions are short-to-medium sequences (a few hundred timesteps at 1–2 Hz) with a small per-timestep feature vector — the exact regime where GRU's lower parameter count tends to match or beat LSTM with less overfitting risk on a modest dataset, while staying cheap enough to run continuously on a laptop CPU. The Transformer is kept as a reported comparison, not the deployed model.

EXHIBIT 08

Dataset strategy

Two datasets, two different jobs: one validates the architecture against a known benchmark, the other validates behavior in the actual deployment domain.

DAiSEE (public benchmark). 9,068 video snippets from 112 users, labeled across four ordinal engagement-related states, collected during online lecture-watching. The standard academic anchor for this exact problem — used here to prove the temporal architecture works against real, citable labels. Its limitations are stated honestly rather than glossed over: short 10-second clips, a demographically narrow population, and a lecture-watching context rather than self-directed study.

Self-collected diary dataset (deployment domain). Short scripted sessions — "look at the screen and type," "look away repeatedly," "read without typing," "leave the desk" — recorded with explicit consent, used to validate the model actually deployed. No raw video is retained past feature extraction; anyone recorded can request deletion.

EXHIBIT 10

Deployment architecture

Two requirements pull in different directions: monitoring must survive the student tabbing away to another site, and the dashboard must be reachable by anyone with a link. A single website can't do both — so this isn't one.

Why a browser tab can't do this alone Browsers deliberately throttle or suspend JavaScript execution — and often stop delivering camera frames entirely — on tabs that lose focus. This is a deliberate power/privacy protection, not a bug to code around. A webcam-monitoring browser tab silently degrades the moment a student switches to another tab, which is the opposite of what an invigilator needs to do.

The resolution: split the system in two.

Local Watcher — a small Python process launched once per study block, running as its own OS process, independent of any browser or tab. It owns the webcam continuously, runs the full perception → feature → temporal-model pipeline, tracks the away-stopwatch, detects phones and a second person in frame, and fires OS-level desktop notifications — all regardless of what has focus on screen. It sends only extracted features and state events to the backend, never video.

Shared Web Dashboard — the normal deployed website: target-block planning, live status, session history, compliance reports, recommendations. This is what gets the public URL anyone can open. It reads and displays what the watcher reports; it never touches the webcam itself.

A
Local Watcher (per student, runs on their machine)
Owns the webcam · runs Layers 1–4 · authenticates to the backend · pushes state events over HTTP/WebSocket
Distributed as a script or a packaged single executable (PyInstaller)
B
Shared Web Dashboard (one public URL, every student's account)
Planning, live status display, history, recommendations · reads what the watcher reports · never accesses a camera
FastAPI + Postgres backend, React frontend — deployed to a public host

A browser-extension middle ground was considered and set aside: it narrows the tab-backgrounding problem but doesn't remove it, and adds real build and review complexity for a project at this stage.

EXHIBIT 11

Development roadmap

Ordered to validate cheap assumptions before expensive ones — and to produce a demoable system at every milestone.

  1. Phase A — Signal feasibility. Confirm raw features actually separate focused/distracted/away before writing any model code.
  2. Phase B — Feature pipeline. A clean, deterministic frame → feature-vector function. The foundation everything downstream depends on.
  3. Phase C — Rule-based baseline. A working end-to-end demo with no deep learning — dashboard, stopwatch, and target-block monitor running on simple thresholds. Also the baseline the trained model must beat.
  4. Phase D — Train the temporal model. GRU primary, LSTM and Transformer as comparisons — only started once B and C exist.
  5. Phase E — Fatigue-pattern autoencoder. Reuses the Phase D feature pipeline.
  6. Phase F — Recommendation engine. Needs several weeks of real target-block history to be meaningful.
  7. Phase G — LLM layer, live notifications, polished dashboard. Wraps trustworthy analytics in language and interface.
EXHIBIT 12

Evaluation methodology

Model-level. LSTM vs. GRU vs. Temporal Transformer compared on accuracy, precision, recall, F1, confusion matrix, inference latency, model size, and CPU/GPU utilization; different window sizes and feature combinations (webcam-only vs. webcam + activity fusion) ablated separately.

System-level. The trained GRU is compared against the Phase C rule-based baseline — an honest test of whether the deep learning model earns its complexity. The away-stopwatch's false-trigger rate is measured against manually logged ground truth. The recommendation engine's suggestions are spot-checked against what a human reviewing the same logs would independently suggest.
